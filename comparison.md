# Workflow Orchestration Comparison

## Why Workflow Orchestration Matters

Workflow orchestration is the automated coordination, management, and execution of complex tasks and processes across distributed systems. It is valuable because:

- **Reliability**: Ensures multi-step processes complete successfully even when individual components fail, with built-in retries and error handling.
- **Visibility**: Provides audit trails, logging, and monitoring so teams can understand what happened, when, and why.
- **Dependency Management**: Automatically resolves task dependencies so steps execute in the correct order.
- **Scalability**: Distributes work across workers/containers, enabling parallel execution and horizontal scaling.
- **Reproducibility**: Codified workflows are version-controlled and repeatable, eliminating "it worked on my machine" problems.
- **Reduced Toil**: Eliminates manual coordination of batch jobs, ETL pipelines, ML training, infrastructure provisioning, and business processes.

## Scoring Rubric

Each orchestrator is scored out of 100 across 12 weighted categories. Higher is better.

| Category | Weight | 0 pts | Partial | Full |

| **Execution Durability** | 10 | Target-based idempotency only | Per-task/step checkpoint | Event-sourced durable execution with transparent replay |

### Scoring Rationale (Notable Decisions)

- **Luigi (38)**: Lowest score. No dependency isolation, no suspend/resume, poor audit trail, poor scalability, and in maintenance mode. Dynamic task creation via `yield` and vendor independence are its only real strengths. **Score unchanged after implementation**, but the testing added a genuinely surprising data point: Luigi needed **6 defects fixed and none of them structural** — fewer than Airflow (14), Kestra (18) or Conductor (15), and its task graphs were correct as committed. Everything that broke was integration detail. The reason is the same reason it scores 38: the model is so thin there is little to get subtly wrong, and every capability the rubric rewards is hand-written application code instead. Cheap to get running, expensive to own. **The 1/10 audit trail is now measured** (2026-08-12): DAG 1 was run through the `luigid` central scheduler rather than `--local-scheduler`, and the scheduler's per-task record is name, params, status, timings and worker — **no inputs, outputs, return values or logs**, because Luigi's unit of state is a Target, so the scheduler knows a task is `DONE` and not what it produced. Retention is `remove_delay=600s`, ten minutes, and `record_task_history` is **False** by default (persistent history needs a separate database you supply, and even then records state transitions, not I/O). Both halves of the rubric's 0-point column are met exactly. Getting there also produced the sharpest maintenance-mode evidence in the comparison: **`luigid` will not start on a current toolchain at all** — `luigi/server.py` 3.7.1 imports `pkg_resources`, removed in setuptools 82, so the daemon dies on import and needs a `setuptools<81` pin whose own deprecation notice gives it an expiry date.
- **Step Functions (60)**: Strong on scalability (serverless), dependency isolation, and auth (IAM + Identity Center), but zeroed out on vendor independence (pure AWS lock-in) and dynamic task creation (immutable state machine). Resume from failure scored low due to Redrive constraints (14-day window, Standard only, same definition).
- **Kestra (63)**: Good isolation for script tasks and language flexibility via YAML+containers, but no dynamic task creation, SSO requires paid Enterprise tier, and slightly younger community.
- **Airflow (65)**: Excellent audit trail and community, but weak on language flexibility (Python only), dependency isolation (shared env by default), and only partial dynamic task creation. Free OAuth2/OIDC SSO is a plus.
- **Prefect (67)**: Excellent dynamic tasks (imperative Python) and dev experience, but Python-only, shared-env by default, and SSO requires paid Cloud Enterprise plan. No built-in auth on self-hosted is fine for VPC deployments.
- **Dagster (68)**: Excellent audit trail and dev experience, but Python-only, shared-env by default, and SSO requires paid Dagster+ Pro plan. No built-in auth on self-hosted is fine for VPC deployments.
- **Google Workflows (70)**: **Up 11 points after implementation (59 → 70)**, the largest score movement in the comparison, and all three moves were corrections of things scored from documentation. *Dynamic task creation 0 → 8*: `parallel` + `for` over a runtime list is real data-driven fan-out, verified with 3 CSVs and a 30-item API response, with `concurrency_limit` for the spec's caps -- the same shape as Argo's `withParam` (8). *Suspend/resume 4 → 5*: `events.await_callback` genuinely suspends the execution -- no worker, no poller, no billed step, up to a year -- which is the best suspend story here; only Temporal matches it, and Temporal needs a worker fleet to do so. *Audit trail 4 → 6*: errors carry step name and line number, and `call_log_level: LOG_ALL_CALLS` logs every HTTP call, though there is still no per-step I/O inspection or execution graph. Still zeroed on vendor independence (pure GCP) and near-bottom on local development, since no emulator runs this DAG set. **The unscored cost the rubric misses**: the engine executes no code of your own, so the four DAGs required a 14-route Cloud Run service before anything could run at all. Deployment is genuinely one command; *building* is not. See "Implementation Friction" below.
- **Flyte (70)**: Strong isolation (K8s-native, verified one pod per task), dynamic tasks via `@dynamic` (verified), and free OIDC SSO in OSS. Requires Kubernetes and has a smaller community. **The score is unchanged after implementation**, and that is worth stating plainly: everything the testing exposed -- the implicit-dependency hazard, `retries=` being inert without `FlyteRecoverableException`, a chart whose defaults cannot execute a workflow, registration that only works in-cluster -- is about *authoring correctness and setup friction*, which this rubric does not weight. Flyte's capabilities are as scored; the cost of getting to a first green run is not in the number. See "Implementation Friction" below.
- **Hatchet (70)**: Strong durability (checkpoint-based, PostgreSQL-backed), multi-language, dynamic tasks, and first-class suspend/resume. Auth is the weakest of all 12 tools -- it forces a built-in user database that cannot be replaced by an external IdP (no SAML, no generic OIDC, no SCIM, no group roles). Having no auth at all would be better since you could front it with your own IdP infrastructure. Also deducted for very young project (Dec 2023), shared-env by default, and log line limits.
- **Argo (74)**: Strong isolation, dynamic tasks via `withParam`, and excellent free OIDC SSO with group-based RBAC. Audit trail is a weak spot (logs lost when pods are GC'd -- now confirmed on a live cluster, repeatedly) and requires Kubernetes. Implementation added one unscored strength worth noting in the deck: Argo **validates the whole call tree at submission**, so structural mistakes cost nothing to find, where the Python-native tools surface them one failed task at a time. `withParam` itself remains unverified here -- Argo's DAG 1 and DAG 2 were not run.
- **Conductor (75)**: Second highest, and the only tool whose workflow definition is *data* -- JSON pushed into the server's metadata store and versioned there -- so the orchestration graph can change without redeploying the code that executes it. Genuine runtime task creation (`FORK_JOIN_DYNAMIC`), the simplest suspend/resume of anything evaluated (one unauthenticated HTTP POST, no SDK, token or relay process), a strong Postgres-backed audit trail with unlimited retention, and the easiest local start (one container; zero external dependencies if you accept its SQLite default). Six actively-maintained SDKs. **Held back by three things**: Conductor OSS has *no authentication at all* -- anyone who can reach the API can complete any task, read every execution and rewrite every definition, so it can only run behind something else (3/5, the same score as tools with no auth, though "none" is at least replaceable, unlike Hatchet's un-substitutable user DB); dependency isolation is shared-worker by default like Temporal and Hatchet (4/10); and durability is per-task checkpointing, not event-sourced replay (6/10). Note the score does **not** displace Temporal: durable execution, timer-accurate timeouts, and true resume-from-exact-failure remain a 13-point gap.
- **Temporal (88)**: Highest score. Event-sourced durable execution is unmatched (10/10). Multi-language SDKs, true dynamic tasks (imperative code), first-class signals, and open source. Self-hosted has free OIDC SSO. Main deductions: shared worker env by default, Cloud SAML requires Business plan ($500+/mo).

## Implementation Friction (measured, not scored)

The same four DAGs were written for every tool and then actually run. What that
cost per tool is the most directly comparable evidence this exercise produced,
and **none of it is in the score** -- the rubric weights capabilities, not how
hard they are to reach. It belongs in a recommendation anyway, because it is a
one-time cost paid by the team that adopts the tool.

Counts are defects found and fixed while making the committed code pass, taken
from each tool's `README.md`:

| Tool | Defects | Verified | Character of what broke |
|---|---|---|---|
| **Temporal** | **0** | all 4 DAGs | Nothing. The only gap was a missing starter client. Ordinary code, executed eagerly, behaved as written. |
| **Argo** | 5 | DAG 3, DAG 4 | All structural, all caught *at submission*: a misplaced template field, `WorkflowTemplate` parameter scoping, un-exported child outputs, `when:` on skipped tasks. Plus the same FK-ordering bug Prefect had, and it was the only implementation of eight not persisting `approval_requests`. |
| **Dagster** | 9 | all 4 DAGs | One structural: the directory could not be named `dagster/` at all -- it shadows the installed library. |
| **Hatchet** | 10 fixes | all 4 DAGs | See `hatchet/README.md`. |
| **Prefect** | 11 fixes | all 4 DAGs | Wrong schema, missing `unmapped()`, FK insert ordering, sample inputs referencing absent seed rows, missing `retry_condition_fn`. |
| **Airflow** | 14 | all 4 DAGs | Two parse-time; and `PYTHONPATH` omissions leave DAG 2/4 stuck in `deferred` silently forever. |
| **Conductor** | 15 | all 4 DAGs | See `conductor/README.md`. |
| **Kestra** | 18 | all 4 DAGs | The most of any tool. All 30 script tasks crashed on an import that exists only in the server's own venv; `execution.resumeUrl` does not exist in any Kestra version. |
| **Flyte** | by class, below | all 4 DAGs | The most *conceptual*. Every one of the four workflows needed structural change before it would even **register**. |
| **Google Workflows** | 12 fixes (7 defect *classes*) | all 4 DAGs | The most *language*-driven. Four fail at deploy time (`{}` is not a literal; `shared:` needs a pre-existing variable), which is the good news. The other three point away from the cause: `list.concat` appends rather than concatenates, a `switch` with `next:` silently skips intervening steps and unset variables serialize as `null`, and a TypeError raised inside a retry predicate *replaces* the original HTTP error -- so a decline branch died with `KeyError: code`. Separately, and larger than any of them: four services the YAML called did not exist, because the engine runs no code. |
| **Luigi** | 6 | all 4 DAGs | **None structural.** The FK-ordering bug shared with Prefect/Argo/Flyte, two missing resume-broker `provider` fields, and documented invocations naming seed rows that don't exist. The task graphs themselves were correct. |

Counts are as stated in each tool's own notes, so the basis varies slightly
(Prefect and Hatchet are numbered fix lists rather than a defect tally) -- treat
them as an order of magnitude, not a leaderboard to two significant figures.

Flyte's is counted by class rather than by site, because the same mistake recurred:

| Class | Sites | Caught at |
|---|---|---|
| `@workflow` constructing its output dataclass from Promises | 5 | registration |
| Branch predicate over nested dataclass fields | 4 | registration |
| Missing explicit `>>` ordering edge | 5 | **run time, as a race** |
| Blob/file handling (`FlyteFile` passing, blob→str binding, HTTP fetch) | 3 | run time + registration |
| Resume-broker `provider` contract | 2 | run time |
| Retriability by exception base class | 1 | run time |
| Schema isolation, FK ordering, `zip` vs `zip_code`, image platform/override | 5 | run time |

Three observations that generalise:

1. **Where a tool catches your mistake matters as much as whether it can express
   the workflow.** Argo and Conductor reject a structurally invalid graph before
   running anything. The Python-native tools discover the same class of problem
   one failed task at a time, and on Kubernetes each of those iterations costs
   minutes of pod scheduling.
2. **Eager execution is worth a lot.** Temporal's zero defects and Prefect's
   relatively shallow ones share a cause: the workflow body runs as ordinary
   Python, so sequential code is sequential and a value is a value. Flyte's
   hardest defects all come from the opposite model -- a body that looks
   imperative but is a graph builder, where statement order is not an ordering
   and a task result is not a value.
3. **Defect count does not track quality — it tracks how much the model can
   express.** Luigi produced only 6 defects and none structural, yet scores lowest
   at 38; Kestra produced 18 and scores 63. A thin model has little to get subtly
   wrong because it does almost nothing for you: Luigi's retries, branching and
   compensation are hand-written application code that no orchestrator ever sees.
   Read the count as *cost to get running*, never as *fitness*.
4. **The two Kubernetes-native tools cost more to *host*, not just to author.**
   Neither Argo nor Flyte can reach the mock services or Postgres without those
   being in-cluster and resolvable under the same names the DAGs use -- a backbone
   deployment plus per-namespace aliases that none of the local tools need. Flyte
   adds a metadata Postgres, a blob store, and a bucket on top, and its task pods
   run in per-project namespaces rather than alongside the control plane, so the
   wiring has to be repeated there. Argo's images are multi-arch, so an arm64
   cluster is free; Flyte's *own* images are too, but `ImageSpec` builds task
   images on the authoring machine and defaults to `linux/amd64`, so a mixed-arch
   shop needs a cross-build path or an in-cluster builder. This is the part of a
   K8s-native choice that a capability matrix never shows.
5. **Defaults that produce a healthy-looking but non-functional install are the
   most expensive failure mode of all.** Flyte's chart configures a blob store it
   does not deploy and gives task pods no credentials for it; both present as
   `Running` pods. A sibling cluster in this evaluation sat that way for 46 days
   with zero executions and nothing surfacing a problem. Nothing in a
   capability matrix predicts that.

## Key Differentiators Summary

### AWS Step Functions
- **Strengths**: Zero infrastructure management, deep AWS integration (220+ services), visual Workflow Studio, Distributed Map for massive parallelism.
- **Weaknesses**: Vendor lock-in to AWS, ASL can be verbose, limited local dev experience.

### Apache Airflow
- **Strengths**: Industry standard for data pipelines, massive plugin ecosystem, Python-native, battle-tested at scale, strong community.
- **Weaknesses**: Scheduler can be a bottleneck, DAGs are not truly dynamic at runtime (Airflow 2.x improved this), UI can feel dated, complex to operate self-hosted. Ecosystem dependency management can be painful -- by default all tasks share the worker's Python environment, so conflicting dependency versions across tasks are impossible without opting into heavier isolation mechanisms (`@task.virtualenv`, `@task.docker`, `KubernetesPodOperator`, or `KubernetesExecutor`).

### Argo Workflows
- **Strengths**: Kubernetes-native (CRD), container-per-step isolation, excellent for CI/CD and data pipelines on K8s, CNCF project. **Validates the entire call tree at submission** -- an unresolvable parameter three templates deep is rejected before a single pod starts, naming the exact path (`templates.order-fulfillment.tasks.check-approval-and-approve templates.manager-approval...`). Of the tools tested, only Argo and Conductor catch structural errors before burning compute; the Python-native tools fail at run time, task by task. Control-plane and executor images are multi-arch, so an arm64 cluster needs no special handling.
- **Weaknesses**: Requires Kubernetes expertise, YAML-heavy, no built-in scheduling (needs Argo Events), steeper learning curve for non-K8s teams. Four authoring traps found while getting DAG 4 to pass, all of them structural rather than typos:
  - **`WorkflowTemplate`s are not encapsulated.** `{{workflow.parameters.x}}` inside a template invoked via `templateRef` resolves against the *calling* workflow, and the template's own `spec.arguments` defaults are ignored entirely. A reusable template that reads a workflow parameter the caller happens not to define fails the whole run at submission. Genuinely reusable templates must take everything as `inputs.parameters` with defaults.
  - **`dag`/`steps` templates do not re-export their children's outputs.** The parent must restate them with `valueFrom.parameter:` (not `path:`, which is only valid on a template that has a container).
  - **`when:` on a task whose dependency was *skipped* still evaluates**, so a condition that dereferences the skipped task's outputs dies with `unable to substitute`. The fix is `depends: X.Succeeded`, which omits the task without evaluating `when` -- and Argo **rejects a DAG that mixes `depends` and `dependencies`**, so converting one task forces converting all of them.
  - Host configuration is literal env values in the YAML, so retargeting a workflow at a different Postgres or service means editing every manifest. Contrast Flyte, where the same settings are a typed workflow input.

### Dagster
- **Strengths**: Asset-centric paradigm (data-aware), built-in data quality/lineage, excellent developer experience (`dagster dev`), type system for IO.
- **Weaknesses**: Newer ecosystem (fewer integrations than Airflow), asset model has a learning curve, smaller community.

### Temporal
- **Strengths**: Durable execution (survives any failure), multi-language SDKs, signals/queries for external interaction, ideal for microservice orchestration and long-running workflows.
- **Weaknesses**: Not data-pipeline focused (no built-in scheduling/sensors), requires understanding of deterministic constraints, operational complexity for self-hosted.

### Kestra
- **Strengths**: Declarative YAML (language-agnostic), 600+ plugins, built-in code editor, API-first, Terraform provider, good for cross-team adoption.
- **Weaknesses**: Younger project, smaller community than Airflow/Prefect, enterprise features require paid tier.

### Prefect
- **Strengths**: Pythonic (decorator-based), easy migration from scripts, excellent UI, hybrid execution model, strong community.
- **Weaknesses**: Python-only, breaking changes between v1 and v2/v3, some features cloud-only.

### Flyte
- **Strengths**: Kubernetes-native, strong typing with automatic serialization, built-in caching/versioning, excellent for ML pipelines, multi-tenancy. Verified in practice: **one pod per task** including every dynamic fan-out element; **typed I/O persisted in the blob store**, so a finished run's outputs are still readable through the API after its pods are gone; **configuration travels as data** -- the DB settings are a `DBConfig` workflow input, so a run can be retargeted at a different host without touching workflow code, which Argo cannot do; and **project × domain multi-tenancy is real**, materialised as one Kubernetes namespace per pair with its own `ResourceQuota`.
- **Weaknesses**: Requires Kubernetes, smaller community, heavier infrastructure footprint, steep initial setup -- and "steep" understates it. The single biggest hazard is conceptual rather than operational:
  - **A `@workflow` body looks like Python and is not.** It builds a graph, and Flyte derives edges **only from data dependencies**. Sequential-looking code runs in parallel whenever the later statement does not consume the earlier one's output: a SQL transform ran concurrently with the unzip that was supposed to precede it and failed on a missing table. Nothing warns you -- not the type checker, not the linter, not registration. Explicit `a >> b` edges are mandatory, and four assigned-but-unused task results elsewhere in the same codebase were latent races of exactly this kind. Airflow and Argo make you declare edges so the mistake cannot happen; Prefect and Temporal execute eagerly so sequential code *is* sequential. Flyte is the only tool evaluated where correct-looking code is silently concurrent.
  - **Local filesystem paths do not survive a task boundary** (one pod per task is the same property that buys isolation). Files must be passed as `FlyteFile`/`FlyteDirectory` blobs.
  - **`retries=` is inert unless the exception subclasses `FlyteRecoverableException`.** Declaring `retries=5` on a task whose "retriable" exceptions inherit plain `Exception` produces zero retries, silently, and makes retriable and non-retriable failures behave identically.
  - **Registration is not a local operation.** `pyflyte register` uploads the code package to a signed URL that names the *in-cluster* blob endpoint, so a workstation client does all the work and then fails on DNS; the client has to run inside the cluster. flytekit also reaches for an OS keyring and fails without one.
  - **The chart's defaults do not produce a working install.** `storage.type: sandbox` configures a minio endpoint the chart never deploys (`--set minio.enabled=true` is silently ignored -- there is no such key), and task pods get no blob credentials because `plugins.k8s.default-env-vars` is empty. Both failures present as healthy pods that cannot execute anything: the sibling cluster in this evaluation sat "Running" for 46 days with zero executions and no indication anything was wrong.
  - **Registration-time rejections point at the wrong node.** Constructing an output dataclass from task results fails with `can not serialize 'Promise' object`, and any non-trivial branch predicate over dataclass fields fails with `MismatchingTypes` naming the *upstream* task's output type. Both are correct diagnoses of the wrong thing.
  - Task pods carry ~70s of scheduling and setup overhead each, so a ten-node workflow takes ten-plus minutes -- fine for ML batch, painful for iteration.

### Luigi
- **Strengths**: Simple and straightforward, battle-tested at Spotify, minimal dependencies, good for simple batch pipelines. Verified in practice: **the fewest structural defects of any implementation tested** — the task graphs were correct as written, and all four DAGs passed after six integration fixes. Target-based idempotency is genuinely useful: re-running a `run-id` skips completed tasks with no engine, no database and no daemon (`--local-scheduler` runs the entire pipeline in the invoking process).
- **Weaknesses**: Limited features (no built-in retry/backfill UI, basic scheduler), largely in maintenance mode, no managed offering, lacks modern orchestration features. What that means concretely, from the implementation: **retries, retriable-vs-terminal classification, conditional branching and saga compensation are all hand-written inside task bodies**, so none of them is visible to the orchestrator. Three consequences measured directly:
  - **The retry loop is silent.** `ProcessPayment` made exactly 5 gateway attempts before failing, and nothing outside the process revealed that — no attempt counter, no event, nothing in the marker file. A forced non-retriable decline failed on attempt 1. Both behaviours are correct and both are invisible.
  - **Branching cannot change the graph.** DAG 4's skip-approval path still scheduled the same 6 tasks as the approval path; the approval task ran and returned `decision: not_required` internally. Argo omits the node, Step Functions routes around it, and both show it in the execution graph.
  - **Compensation ends the run `Failed`.** Hand-rolled unwinding worked correctly — reservations released, order cancelled with a reason, inventory restored — but Luigi reports only `1 failed`, so "compensated cleanly" and "crashed" are indistinguishable without reading the database.

### Hatchet
- **Strengths**: Simple PostgreSQL-only architecture (easy to self-host, no Cassandra/Redis/Kafka), durable checkpoint-based execution, one-off background tasks are first-class (no workflow boilerplate needed), multi-language SDKs (Python, TypeScript, Go, Ruby), built-in observability (OpenTelemetry, Prometheus, logging, UI), flexible concurrency controls (rate limiting, priority scheduling, GROUP_ROUND_ROBIN), MIT licensed with no source-available restrictions, no fixed fan-out limits.
- **Weaknesses**: Very young project (created Dec 2023, still pre-1.0), smaller community (~7K stars), no per-task dependency isolation without separate workers, PostgreSQL-only backend limits flexibility, not Kubernetes-native (no CRDs/operator), fewer SDKs than Temporal.

### Conductor
- **Strengths**: Workflow definitions are JSON held and versioned *server-side*, so orchestration changes deploy without touching the workers -- a separation no other tool here provides, and `version` keeps in-flight executions on the graph they started with. Genuine runtime task creation via `FORK_JOIN_DYNAMIC` (a worker returns task descriptors; the engine materialises them, and they may be heterogeneous types or sub-workflows). Retry policy, timeouts and concurrency caps are declared on the *task definition*, so every workflow referencing a task inherits one policy. `WAIT` tasks suspend at zero cost and resume via a single unauthenticated HTTP POST -- no SDK, token, or relay process, the only tool evaluated that needed no new infrastructure for the callback DAGs. `failureWorkflow` gives sagas a first-class trigger and inherits the failed run's whole input. Single container plus Postgres, no Elasticsearch (`indexing.type=postgres`) and no Kubernetes; workers *poll*, so they need no inbound port and work behind NAT. Apache 2.0 with no orchestration primitive gated behind Orkes. Battle-tested since 2016 at Netflix, Tesla, LinkedIn and J.P. Morgan; 32K+ stars.
- **Weaknesses**: **No authentication whatsoever in OSS** -- the UI and the entire API are open, which makes a network boundary mandatory rather than optional. Task timeouts are enforced by a background sweeper rather than timers and fire measurably late (a 60s timeout observed at 103s; a 120s one at 180s), so they are a floor, not a deadline. The expression language does nothing but substitute values -- no arithmetic or comparison -- so every branch condition must be precomputed by a worker, and the JSON is not self-describing as a result. `outputParameters` are evaluated even on failed runs, so literals leak into the output of failures. Definitions living server-side means the repo is not the source of truth and nothing detects drift. Netflix has stepped back to an internal fork, leaving Orkes as sole steward; SDKs are actively maintained but individually small (23-98 stars). The Python SDK spawns one OS process per task type (1.72 GB RSS for 26). No per-task dependency isolation without separate workers.

### Google Workflows
- **Strengths**: Fully managed serverless, deep GCP integration, pay-per-use, and the best suspend/resume in the comparison — `events.await_callback` holds a genuinely suspended execution for up to a year at zero cost (verified). Data-driven fan-out with a concurrency cap. Deploys in one command, with server-side revisions that in-flight executions stay pinned to. Dependency isolation is inherent, since every step is a call to a separately deployed service.
- **Weaknesses**: Vendor lock-in to GCP, limited community, YAML-only, no open-source option, and no local path — this DAG set was only ever run against real GCP. Two costs that only appear on contact: **the engine runs no code**, so every step body is a service you build, deploy, and operate yourself (14 routes here); and the expression language is small with sharp edges — seven distinct defect classes surfaced during implementation, three of which failed at runtime pointing somewhere other than the cause. Retry classification sees HTTP status only, so retriability has to be designed into the APIs the workflow calls. See `google-workflows/README.md`.

## Considered but Not Evaluated

- **Faktory (Enterprise)** — Polyglot background-job server (by Sidekiq's author); its only orchestration primitive is nested batch/callback workflows (a tree of fan-out/fan-in groups, same model as Sidekiq Batch), with no arbitrary DAG or multi-parent dependency support. Orchestration is a paid Enterprise feature ($299/mo, license only), so it was not tested and does not fit the DAG-orchestrator category this comparison targets.

- **Itential** — A real orchestration engine, but in an adjacent category: network and infrastructure automation (Gartner lists it under *Network Automation Platforms* and *Infrastructure Automation & Orchestration Tools*, not data/application orchestration). The engine primitives are genuine and would cover most of this comparison's DAGs — `childJob` for sub-workflows with a documented looping pattern for fan-out, per-task automatic retry with configurable attempts and delay, manual tasks with group-based access control as a native human-approval suspend, job pause/resume with persisted state (pause propagates into child jobs), and schedule/event/API triggers with per-job history in Operations Manager. Saga compensation would be hand-rolled from failure transitions, as in Airflow. **Arbitrary code is fully supported** — a `runCode` task executes inline Python on the Studio canvas, and `runService` invokes a registered Itential Gateway service, which runs Python scripts, Ansible playbooks, OpenTofu plans, or Nornir modules with per-service Python virtualenvs, auto-synced from a GitHub/GitLab/Bitbucket repo. All four of this comparison's DAGs are therefore implementable; the only uncertain piece is DAG 2's suspend-on-external-HTTP-callback, for which no task-token/callback-URL primitive is documented (job pause/resume and a manual-task completion API exist). Excluded for three reasons, none of them capability: *workflow topology* is authored visually in Studio rather than in a source file, which defeats this repo's premise of code-as-evidence (individual step bodies are ordinary code, but the graph is not); it is commercial-only with no published pricing and no free local evaluation path, so it could not be run against the same four DAGs as everything else here;  and its 300+ adapters target network devices, cloud platforms, and ITSM (ServiceNow) rather than the data-pipeline and transactional workloads these four DAGs exercise. **Self-hosting is fully supported and is not the blocker** — [Itential Deployer](https://github.com/itential/itential.deployer) is a public GPL-3.0 Ansible collection covering four validated architectures (All-in-One, Minimal, Highly Available, Active/Standby), with All-in-One explicitly recommended for dev and CI/throwaway environments; the gate is that Platform binaries and IAG wheels come from Itential Nexus, which requires a sales-issued account. The self-hosted footprint is **MongoDB (primary store) + Redis (cache and cross-node coordination)** plus Node.js and Python runtimes, with optional HashiCorp Vault and Prometheus/Grafana — heavier than Hatchet's single-Postgres story and roughly comparable to Temporal's. The Apache-2.0 open source is the *adapters* (`@itentialopensource` on GitLab/npm) and the Deployer; the platform core is not. Credible vendor — ~175 employees, $25.5M raised through a 2021 Series B, five consecutive years as a Gartner Representative Vendor. **If the driving use case were network/infrastructure config automation rather than data and application workflows, Itential would belong on the shortlist and much of this comparison would not.**
